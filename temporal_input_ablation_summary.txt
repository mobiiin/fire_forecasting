B. CONTROLLED PROTOCOL

- Architecture: ConvLSTM U-Net (`convlstm_unet`) for all three runs; 129 input
  channels, 4 output channels, hidden dimension 64, one ConvLSTM layer,
  3x3 kernel, dropout 0.0, and 64x64 patches. Apart from fields necessarily
  derived from the temporal pattern/input length and run identity/paths, the
  recovered resolved configurations use the same architecture, loss, optimizer,
  normalization path, split, batch protocol, and training controls.

- Seed(s): one run per condition. No training seed is explicitly serialized in
  any recovered config/checkpoint. `src/training/train.py` resolves a missing
  training/top-level seed to 42, so the effective seed is 42 if the recovered
  config was executed by the matching trainer behavior. The fixed validation
  subset seed is explicitly stored as 42. This is a single-seed screening
  ablation, not a multi-seed experiment.

- Training budget: `training.max_epochs=20`; all three histories contain 20
  completed epochs and selected epoch 20. The inherited legacy top-level
  `epochs=50` is present, but the resolved training section overrides it with
  `max_epochs=20`. Each epoch was capped at 100 train batches with batch size
  128 (12,800 sampled patches per epoch), gradient accumulation 4, AdamW, and
  the same early-stopping rule (val_loss, minimization, patience 8, min_delta
  0.001, start epoch 5). None stopped early.

- Train split: manual full-fire holdout using
  THOMAS__1204__keepz_08 and THOMAS__1208__keepz_08.

- Validation split: manual full-fire holdout using
  THOMAS__1209__keepz_08.

- Configured test split: manual full-fire holdout using
  THOMAS__1210__keepz_08. It was not evaluated by these training runs:
  `run_test_after_training=false` and `run_external_test_after_training=false`.

- Prediction horizon: target at current/latest-input index +10 processed-frame
  indices for every condition; target definition
  `interval_consumed_current_to_horizon_target_v1`.

- Checkpoint selection: minimum fixed-subset validation loss (`val_loss`), with
  the same fixed subset used for checkpointing. Best epoch was 20 for all runs.
  Exact best val_loss values were 4.010369548797607 (consecutive),
  4.357753434181213 (single), and 3.9596778482630635 (sparse).

- Evaluation protocol: patch-level validation, not full validation and not the
  held-out test. Validation used sequential batches (fixed-subset shuffle false),
  batch size 128, and at most 50 batches:
  * consecutive: 50/51 batches, 6,400/6,504 samples;
  * single: 50/52 batches, 6,400/6,552 samples;
  * sparse: 48/48 batches, 6,072/6,072 samples.
  The valid temporal windows, and therefore validation population/count, differ
  as a direct consequence of the input offsets. Thus the intended experimental
  change is temporal context, but the evaluated sample sets are not identical.

- Input normalization: enabled and applied by the dataset to 129 channels. All
  three checkpoints record the same path:
  /scratch/mhabibp/cawfe_datasets/cawfe_engineered_v1/normalization/latest_normalization.json

C. EXACT TEMPORAL INPUT DEFINITIONS

Let t be `current_index`, the most recent input state in the temporal sample
index. The code computes each input as `t + input_offset` and the target as
`t + horizon`.

Single timestamp:
- number of frames: 1
- exact indices: [t]
- exact spacing: not applicable
- target: t + 10 processed-frame indices

Five sparse timestamps:
- number of frames: 5
- exact spacing: 10 processed-frame indices between adjacent inputs
- exact indices: [t-40, t-30, t-20, t-10, t]
- input span: 40 processed-frame indices
- target: t + 10 processed-frame indices

Five consecutive timestamps:
- number of frames: 5
- exact spacing: 1 processed-frame index between adjacent inputs
- exact indices: [t-4, t-3, t-2, t-1, t]
- input span: 4 processed-frame indices
- target: t + 10 processed-frame indices

The recovered code/configuration does not attach timestamps or an authoritative
wall-clock cadence to these indices. Therefore the sparse spacing is verified
as exactly 10 processed-frame indices, but it cannot be reported as exactly
10 minutes from the recovered evidence. Likewise, the prediction target is
verified as 10 processed-frame indices beyond the latest input, not as exactly
10 wall-clock minutes. The checkpoint metadata field
`target_offset_from_last_input=10` agrees for all three runs.

G. INTERPRETATION -- FACTS ONLY

- Relative to one timestamp, five consecutive inputs have higher Dice and IoU
  and lower Surface and Canopy MAE. One timestamp has a slightly lower Energy
  Log MAE and higher recall, while five consecutive has higher precision.
  Therefore, the observed advantage of consecutive history over a single state
  is not uniform across every target/metric.

- Five consecutive inputs do not uniformly outperform the longer-span sparse
  inputs. Five sparse has higher Dice and IoU, whereas five consecutive has
  lower Energy Log, Surface, and Canopy MAE. For the additional RMSE metrics,
  consecutive has lower Energy Log and Canopy RMSE, while sparse has lower
  Surface RMSE.

- The results therefore show a segmentation-versus-regression tradeoff rather
  than one temporal pattern winning every stored metric. Active Canopy MAE
  cannot inform this comparison because it is NaN for all three runs.

- These observations are from one validation-screening run per condition and
  do not establish statistical significance or performance on the held-out
  test fire.

H. UNCERTAINTIES / MISSING INFORMATION

- Wall-clock cadence is not recoverable from the temporal indices/configs, so
  neither the 10-index sparse spacing nor the +10-index target horizon can be
  certified as minutes.

- The training seed is not explicitly stored. Seed 42 is inferred from the
  fallback in the present trainer code; the completed runs' Git commit/code
  snapshot was not recovered, so this inference is marked rather than treated
  as direct checkpoint metadata. Fixed validation seed 42 is directly stored.

- The original run directories, Slurm stdout/stderr files, and separate
  evaluation products are absent. Exact metrics survive in the recovered
  best checkpoints, whose hashes are recorded above.

- The mutable normalization path is stored but no normalization-file hash or
  run-local copy was found. Its exact contents as of 2026-08-14 cannot be
  reverified. All three checkpoints nevertheless record the same path and the
  same 129-channel shape.

- No held-out-test, full-validation, no-fire-subset, or multi-seed results were
  found for this temporal ablation. Active Canopy MAE and the other stored
  active log/fuel MAEs are NaN at the selected epochs.

- Validation sample populations are not identical: the temporal offsets change
  which current indices are valid, and sparse uses 6,072 samples while the
  other selected subsets use 6,400. This limits a strict paired-sample reading.

- No evidence was found for a 10^2 or 10^3 paper-display scaling convention for
  these runs, so scaled values are intentionally not invented.

- The statement that five consecutive inputs were eventually used by the final
  model is not supported by the current repository state. The recovered
  `configs/default.yaml` names consecutive5_h10 as its generic default pattern,
  but current `configs/experiments/cawfe_latte_v1.yaml` and
  `configs/experiments/cawfe_latte_baseline.yaml` explicitly select
  sparse5_h10. A historical final-model config proving a dense-consecutive
  selection was not found.
